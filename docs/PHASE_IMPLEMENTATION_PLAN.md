## 1. 最終目標

多様な複合感情を呼び起こす音楽を、曲全体の構造を通じて生成する。単に反復を少なくするのではなく、導入・提示・発展・対比・回帰・終結が、ひとつの音楽的な因果関係として成立することを目指す。特定ジャンルや作曲家の模倣は手段であり、最終目標ではない。

## 4. 各フェーズの詳細

### Phase 0 — 生成基準と比較契約
- **入力**: 指示文、感情指定、編成、生成シード、旧／新エンジンフラグ。
- **作業**: 同一条件の再現、生成トレースの保存、再生音量の比較条件の統一。表示上の名称と実際の生成処理を一致させる。
- **成果物**: 比較条件仕様、再現可能なfixture、比較画面、回帰テスト。
- **ゲート**: 生成フラグをOFFにすると旧経路が維持される。比較画面から同一条件のA/Bを再生できる。

### Phase 1 — 曲構造と感情目標
- **作業**: セクション種別、長さ、役割、感情ベクトル、緊張と解放の到達点、セクション接続の定義。
- **成果物**: `CompositionPlan`/`SectionPlan`相当のデータ契約と診断出力。
- **ゲート**: 曲の構造が生成より前に存在し、生成後の音符と対応付く。OFF/ON比較では感情表現以外の条件を固定する。
- **留保**: 既存コードに相当する実装があるため、再実装ではなく不足箇所の検証・改善を優先する。

### Phase 2 — 全曲の主題展開
- **作業**: 提示・対比・展開・回帰の配置を先に決める。どの動機をどのセクションで引用するかを計画し、Mラインの動機エンジンに引き渡す。
- **成果物**: `motifReference`、セクション間の関係、回帰予定、長期的な終止計画。
- **ゲート**: 冒頭の主題が中盤・終盤で認識可能な形で現れる。単純な小節コピペに頼らない。

### Phase 3 — 曲構造に従う編曲
- **作業**: セクションごとに主旋律・低音・和声・対旋律・リズムの役割を割り当てる。楽器の入退場、音域・密度、ソロ・ユニゾンを制御する。
- **成果物**: `ArrangementPlan`/`VoiceRole`相当。音色と編成の変更を生成トレースに残す。
- **ゲート**: 重要な旋律が埋もれず、楽曲のピークと静かな部分に編成差が出る。

### Phase 4 — セクションの接続
- **作業**: 移行部、ブレイク、共通音・リズムによる予告、和声や低音による誘導、長いフレーズにおける呼吸位置を計画する。
- **ゲート**: セクション境界で楽器・リズム・和声が理由なく突然変化する問題が減る。

### Phase 5 — 全曲監査
- **作業**: セクション長、反復・対比の比率、感情曲線、音域推移、音楽的到達点を計画と実際の出力で照合。修正は必要なセクション単位に限定する。
- **ゲート**: 全曲レベルの矛盾が検出・説明でき、修正が既存の良い部分を壊さない。

### Phase 6 — 統合評価
- **作業**: 曲構造のみ変更、Mラインのみ変更、両方変更の3条件を基準と比較。固定シード複数曲で聴取記録を蓄積。
- **ゲート**: 「曲としてのまとまり」「変化に理由があるか」「再び聴きたくなるか」を記録し、未改善なら次の変更対象を特定する。

## 5. Mラインとの境界

**フェーズラインが所有:** 曲の全体構成、セクション役割、感情推移の計画、楽器の大きな出入り、楽曲全体の接続。  
**Mラインが所有:** 動機の具体的な変形、音程・リズム・休符、和声の実現、対旋律、表情付け、局所的評価。  
**共通:** データ契約・シード・生成トレース・比較UI。共通ファイルは同時変更せず、契約を先にマージする。

## 7. 開発ルールとテスト

- 既存の `DEVELOPMENT_RULES.md` を遵守。事前にソース、HTML、API export、テストモック、CI構成を確認する。
- **影響しそうな既存テスト**: `tests/preflight-contracts.test.cjs`、曲構造／感情アーク／動機展開／編曲／音源／UI関連のテスト（実ファイル名は棚卸し時に確定）。
- 既存Node/jsdom等のテスト環境・書き方に合わせる。作曲結果の決定性、旧挙動、DOM契約、生成処理のON/OFFを回帰確認する。
- 各変更: (1)差分レビュー (2)構文・CI (3)最新Previewの画面操作 (4)固定シード聴取比較を**別々に記録**する。
- Issue/PRへ再現手順、確度付き原因、変更点、CI結果、Preview/聴取結果、未解決事項を記録する。

## 8. 直近の実施順（再作業を防ぐ）

1. 既存Phase 1、動機展開、楽器の出入りに関する実装・テスト・A/B画面を棚卸しする。
2. 実装済み／部分実装／未実装を分けて、Phase 2以降にある重複タスクを削除する。
3. 共通 `CompositionPlan` の最小契約をMラインと確定する。
4. Phase 2の**セクション→動機参照**のみを最小PRとして接続する。
5. 変更ごとのCI・Preview・聴取の証跡を残す。

## 9. 完了の定義

すべての段階で、技術的完了と音楽的完了を分ける。CI成功、Vercel READY、音源再生可能のいずれか単独では「音楽的改善」を意味しない。聴取評価で改善が確認できなければ対象の段階を再調整する。
