# plotune Mシリーズ実装計画書

版: 1.0 / 2026-10-22
対象: `al1ce4869999999-ux/plotune`
位置づけ: **音楽表現・動機発展・和声・声部・演奏表現を担当する開発ラインB**
関連文書: `PHASE_IMPLEMENTATION_PLAN.md`, `DEVELOPMENT_RULES.md`

## 1. 最終目標

聴き手が感情の移り変わりを感じられる、階層的で一貫性のある楽曲生成を実現する。ベートーヴェンの動機発展、ショパンの旋律と表情、バッハの声部独立性を技法上の参考とするが、作曲家の表層的模倣や固定パターンのランダム混合は行わない。

中心仮説: **音楽的な記憶を保持し、旋律・和声・声部・演奏を感情と構造に応じて相互調整すれば、単なる音符差分よりも意味のある変化を作れる。**

## 2. 原則

1. 感情ラベルからコードや音程を一対一で機械的に決めない。
2. 曲全体の感情・構造計画を入力に、複数の音楽的候補を作る。
3. 動機の同一性と変化を両立させる。無意味な反復も無関係なランダム変化も避ける。
4. 和声・旋律・リズム・声部・演奏は相互依存させる。
5. 理論ベースの自動評価と、実際の聴取評価は別に扱う。
6. 既存エンジンの出力経路・音色・シードとの互換性を維持する。

## 3. 全体計画

| 段階 | 中心成果 | 細分化した変更 | 受け入れ条件 | 主な依存 |
|---|---|---|---|---|
| M0 既存資産と契約 | 既存実装の再利用方針、比較基準 | 公開API調査→データ契約→fixture→フラグ設計 | 既存機能を残し、独立比較が可能 | Phase 0/1 |
| M1 動機記憶・発展 | 動機が曲を通じて再登場 | 抽出・登録→変形→履歴→回帰 | 主題の識別性を保ちながら発展できる | SectionPlan |
| M2 感情連動フレーズ | 感情による旋律構造の変化 | 感情ベクトル→旋律目標→リズム・休符→終止 | 音色だけでなく旋律・リズム・終止が変化 | M0/M1 |
| M3 和声的ドラマ | 旋律と和声の共生成・再解釈 | 和声目標→候補→声部進行評価→再和声化 | 同主題に異なる和声的意味を持たせられる | M1/M2 |
| M4 声部の対話 | 独立して意味を持つ低音・対旋律 | 声部役割→応答→模倣→音域制約 | 主旋律を壊さず声部間の掛け合いができる | M3、Phase 3 |
| M5 演奏・表情 | フレーズに沿った演奏情報 | 強弱→音価・間→ルバート→装飾→楽器特性 | フレーズの頂点と終止が演奏に現れる | M2、Phase 3/4 |
| M6 評価・局所修正 | 作曲結果への根拠ある改善指示 | 指標→原因位置→候補再生成→採否 | 既存の良い部分を維持して問題箇所を修正 | M1〜M5 |
| M7 統合・聴取検証 | 全体の改善を判断できる | 機能別A/B→組合せA/B→聴取票→結果記録 | 技術的成功と聴感改善を区別して評価 | 全段階 |

## 4. 共通データ契約

仮の概念スキーマ（実ファイルや実際のexport名を指定するものではない）:

```text
CompositionPlan
  seed / instrumentSet / sections[] / globalEmotionTrajectory
SectionPlan
  sectionId / role / length / emotionTarget / tensionTarget
  motifReferences[] / cadenceTarget / voiceRoles[] / arrangementTarget
Motif
  motifId / pitchIntervals[] / rhythmPattern[] / accents[]
  harmonicContext / expressiveRole / variationHistory[]
PhrasePlan
  phraseId / sectionId / motifId / contourTarget / rhythmTarget
  breathingPoints[] / cadenceTarget / harmonicTargets[]
MusicScore
  notes[] / harmonyEvents[] / voices[] / performanceEvents[]
GenerationTrace
  decisionId / scope / candidates[] / chosenCandidate / reasons[]
  evaluationMetrics / sourceSeed
```

原則: **Phaseラインが計画を作成し、Mラインが音楽的内容を実現する**。設計で特定した受渡し口以外から、互いの内部状態を直接書き換えない。

## 5. M0 — 既存実装の棚卸し

### 作業
1. 既存の動機発展、フレーズ生成、感情計画、和声生成、楽器配置、`generationTrace`の実装箇所を確認。
2. 類似機能を新規に作らず、機能単位で「再利用／拡張／置換」の判断表を作る。
3. 比較条件を既存のPhase 1 OFF/ON比較と干渉しない形で固定。
4. 最小のデータ契約と明示的な機能フラグを定義。

### 完了基準
公開APIとDOMモックの契約を破らず、旧経路の生成結果が維持される。固定シードの出力が比較できる。

## 6. M1 — 動機発展

### サブタスク
- M1-1 動機登録（音程間隔、リズム、アクセント、和声背景）
- M1-2 反行、拡大・縮小、リズム変形、断片化、移高を**個別**に実装
- M1-3 セクション間で動機の登場履歴と変形理由を保持
- M1-4 主題回帰で、認識可能性と変化量のバランスを制御
- M1-5 動機の一致・反復・差異を解析してトレースに表示

### テスト
元の動機から変形後の音符が理論どおり導かれること。休符・小節境界・音域・拍節上の制約を保持。M1 OFFで旧生成と互換。固定シードで決定的。

### 聴取課題
同じ曲の冒頭と終盤で「同じ主題の変化した回帰」を聴き取れるか。

## 7. M2 — 感情連動フレーズ

### サブタスク
- M2-1 感情を複数軸の連続値（緊張、活性、安定、親密さ等）として受け取る
- M2-2 感情目標→輪郭・音域・跳躍・密度・長さへの候補制約を生成
- M2-3 リズム・休符・音価・終止をフレーズ単位で選ぶ
- M2-4 固定的な「悲しい=下降音形」などの単純規則を回避し、複数候補から選択

### テスト・完了
感情だけを変更した固定条件で、旋律構造が変わる。異なる感情で同一音型に過度に収束しない。フレーズ終止が成立する。

## 8. M3 — 和声的ドラマ

### サブタスク
- M3-1 フレーズごとの到達和声、緊張、終止機能を計画
- M3-2 旋律候補と和声候補を並行生成し、声部進行と和声音・非和声音を評価
- M3-3 経過的・準備された不協和、転調、借用などを制約付きで扱う
- M3-4 主題回帰時の再和声化を行う

### テスト・完了
同じ旋律に対する異なる和声解釈を生成し、理由を記録。和声変更に合わせて旋律が破綻しない。終止・転調の境界が説明できる。

## 9. M4 — 声部間の対話

### サブタスク
- M4-1 主旋律、対旋律、低音、内声の役割を明示
- M4-2 応答・模倣・反行・リズム補完パターンを選択可能にする
- M4-3 声部間の過密、不要なユニゾン、音域干渉、不自然な跳躍を検査
- M4-4 必要な場面のみ対位法的密度を高める

### テスト・完了
対旋律が独立した運動を持ち、和声的な整合性が保たれる。声部をOFFにしても主旋律・低音の基本機能が壊れない。

## 10. M5 — 演奏表現と編曲との接続

### サブタスク
- M5-1 フレーズ頂点と終止に応じた強弱カーブ
- M5-2 呼吸・フェルマータ・ルバートの局所計画
- M5-3 装飾音の条件付き追加（生成済み主題の輪郭を壊さない）
- M5-4 楽器ごとの発音・余韻と、Phase 3の入退場計画を合成

### テスト・完了
同じスコアの表情ON/OFFでタイミング・強弱差を説明できる。音量差だけによる優劣錯覚を避けるため、比較時はラウドネス条件を配慮する。

## 11. M6 — 品質評価と局所再生成

### サブタスク
- M6-1 同一小節の反復、動機同一性、無関係な変化、終止、和声解決、声部独立性を別指標で評価
- M6-2 問題発生位置と原因候補を出力
- M6-3 小節・フレーズ単位の再生成を提案し、変更前後の評価を比較
- M6-4 トレードオフを残し、単一総合スコアの最大化で個性を失わない

### テスト・完了
局所修正で無関係なセクションが変化しない。改善後も主題の同一性・曲全体の計画が維持される。

## 12. M7 — 評価と統合

### 比較条件
- ベースライン（既存エンジン）
- Phaseラインだけ有効
- Mラインだけ有効
- 両ライン有効
- 必要に応じM1〜M5を一つずつOFFにするアブレーション

### 聴取観点
1. 冒頭の主題を記憶できるか。
2. 再登場時に元の主題だと分かるか。
3. 同じ主題の感情的意味が変わるか。
4. 和声・リズム・声部・演奏が自然に連携しているか。
5. 曲全体が無意味なループや寄せ集めに聞こえないか。

### 完了基準
同一条件の複数曲で上記を記録し、定量指標と聴取評価の食い違いも報告できる。改善が不明な場合は「達成」としない。

## 13. 並行開発と統合ゲート

| M作業 | 同時に進められるPhase作業 | 統合の前提 |
|---|---|---|
| M0 | Phase 0/1 再確認 | フラグ、シード、共通データ契約 |
| M1 | Phase 2 構造・再現 | motifIdとSectionPlanの参照契約 |
| M2 | Phase 2 後半、Phase 4の設計 | emotionTarget、cadenceTarget |
| M3 | Phase 3 編曲の計画側 | 声部役割と和声イベントの契約 |
| M4 | Phase 3 楽器配置 | 声部と楽器を別概念として管理 |
| M5 | Phase 4 セクション接続 | 演奏イベント・境界位置 |
| M6 | Phase 5 全曲監査 | 評価指標と改変許容範囲 |
| M7 | Phase 6 統合 | 共通比較UIと結果記録 |

同一ソースの並行編集は避ける。共通契約の変更は小PRで先に確定し、以降はモジュール単位で変更する。

## 14. 既存テストへの影響と品質手順

- 想定される既存テスト群: `tests/preflight-contracts.test.cjs`、既存の作曲エンジン、動機・フレーズ、感情アーク、和声、編曲、UI、音源出力の各テスト。**実ファイル名・テストランナーはM0で棚卸し**。
- 新規テストは既存のNode/jsdom等のスタイルに合わせる。公開API名を推測せず、実コードから確認する。
- 各変更は単機能・単目的。既存OFF動作、決定性、HTML資産、DOMモック、音源出力の退行を確認する。
- 自動CI、最新Preview操作、Safari実機、聴取比較は区別し、未確認を確認済みと書かない。
- 不具合は再現・事実上の原因・修正・CI/Preview結果・残課題をIssue/PRに記録する。

## 15. 着手順

1. M0-1 実ファイル・公開API・生成経路の棚卸し
2. M0-2 旧エンジン・既存Phase 1 OFF/ON比較の再利用方式を決める
3. M0-3 Phaseラインと共通のスキーマ・機能フラグを最小PRで固定
4. M1-1 既存の動機発展実装を再利用し、追加が必要な変形だけを追加
5. 最初の「主題→変奏→回帰」の固定シードA/Bを聴取評価する

## 16. 成果報告の形式

各作業の報告は「変更対象／変更内容／影響する既存テスト／CI結果／Preview確認／聴取評価／残課題」を区別し、未実行・未確認を明記する。GitHubのCI成功を音楽的完成と呼ばない。
